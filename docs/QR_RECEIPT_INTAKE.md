# ПрихРасх — «Чек по QR»

## Решение владельца (15.10.2026)

Существующая Google-форма остаётся штатным способом ввода. Дополнительный режим «Чек по QR» запускается отдельной мобильной страницей. Старые ответы и аналитика не меняются.

Рабочая форма:
(ссылка вводится пользователем в интерфейсе и хранится только на устройстве)

## Этап 1 — изолированный сканер, безопасный пилот

В этой ветке реализованы:
- web/qr/index.html — мобильная страница выбора между обычной формой и чтением QR.
- web/qr/fiscal-qr.mjs — чистый парсер шести фискальных реквизитов: t, s, fn, i, fp, n.
- tests/tooling/fiscal-qr.test.mjs — синтетические unit tests без настоящих финансовых данных.
- Камера и фотография используются только локально посредством BarcodeDetector. В неподдерживаемом браузере есть ручная вставка текста QR.
- Валидация суммы производится в целых копейках, дата чека не преобразуется в часовой пояс устройства.
- Кнопка открывает обычную форму, но не утверждает, что она уже предзаполнена.

Ограничения пилота:
- Пока нет подключения к API полного электронного чека и списка товаров.
- Нет отправки ответа в Google Forms и записи в Google Sheets.
- Нет публикации страницы на production HTTPS.
- Нет новых сервисных ключей, секретов, БД или YDB writer.
- QR реквизиты, фотографии и финансовые данные не публикуются в репозитории.
- Для camera access нужен HTTPS и поддерживаемый браузер; BarcodeDetector может быть недоступен.
- Нет предположения, что сканирование QR само по себе доказывает подлинность чека.

## Этап 2 — полноценный пользовательский сценарий

После пилота реализовать один вертикальный сценарий:

1. Сканировать QR, извлечь дату, сумму, ФН, ФД, ФП и тип операции.
2. Серверным защищённым запросом получить полный электронный чек через выбранного провайдера. Проверить API-доступ, цену, задержку, ограничения использования и долю полученных чеков до интеграции.
3. Создать draft с магазином, товарными строками, итогом в копейках и исходной фискальной identity. Никаких автоматических записей до review.
4. Разнести товарные позиции по существующим категориям ПрихРасх с возможностью исправления.
5. Пользователь выбирает реальный платёжный счёт и подтверждает расход. Учитывать правила Visa/Credit/Наличка и «Вика» из docs/FINANCIAL_SEMANTICS.md.
6. Подтвердить invariant: сумма распределённых позиций равна итогу чека, без удвоения общей суммы; корректно учитывать скидки и возвраты.
7. Проверить реальные поля и поведение Google-формы, затем либо prefill/submit через поддерживаемый механизм Forms, либо отдельный adapter c точно эквивалентными схемой, валидацией и trigger-semantics.
8. До cutover transactional authority — только Google Sheets, лист «Ответы на форму (11)», как предписано docs/SOURCE_ADAPTER_CONTRACT.md.
9. Persisted idempotency по сочетанию ФН + ФД + ФП и состоянию подтверждённой отправки. Повторная отправка не создаёт дубли.
10. При unavailable receipt API — открывать старую Google-форму, не придумывать товары и продавца.

## Пределы безопасности и выпуска

- Отдельная ветка и draft PR. Пока R1 точечный provider proof не завершён, продуктовый PR не сливать в main.
- Не менять origin/form, существующие ответы, исторические строки, отчёты и YDB authority.
- Нет private receipt fixtures; тесты только на синтетических реквизитах.
- Никаких ключей API на клиенте, в публичном репозитории и логах.
- Продакшен-выпуск только после security/permissions review, пилота на реальных чеках вне публичных артефактов и reconciliation.

## Приёмка текущей ветки

Команда:
node --test tests/tooling/fiscal-qr.test.mjs

Проверить на HTTPS с Chrome для Android:
- чтение бумажного QR камерой и прекращение доступа к камере;
- загрузку фотографии;
- корректную сумму и дату;
- невозможную дату, отсутствующие поля и повторяющиеся поля;
- отсутствие сетевой передачи чека и финансовых записей;
- переход к исходной Google-форме.
